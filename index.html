automacliVárias branches. Várias stacks. Uma máquina.

Cada branch vira uma task com diretório, slot e portas próprios. Bancos e caches sobem uma vez e são compartilhados. Sem conflito de porta, sem reinstalar dependências, sem esperar a vez.

🌿

Uma task por branch

Três PRs para revisar e uma feature pela metade, num checkout só: stash, checkout, install, e amanhã tudo de novo.Cada branch vira um diretório próprio, pronto para rodar. Trocar de contexto é um cd.

🔌

Portas por slot

A segunda stack não sobe: port is already allocated. Ou você edita portas no compose e suja o git.Cada task ganha um deslocamento de portas e um projeto compose próprio. O override é gerado fora do git; você não edita nada.

🗄️

Serviços compartilhados

Um Postgres por cópia: seed de novo, memória em dobro. Ou todas as cópias brigando pelo mesmo banco, e um down derruba o das outras.Banco, cache, busca e fila sobem uma vez, no repo base, e atendem todas as tasks. Nenhuma task consegue derrubá-los.

⚡

Clone em segundos

Cada clone novo repete pnpm install, composer install e minutos de download.A task nasce de um snapshot do repo base com node_modules, vendor e caches já quentes. Menos de um segundo, sem gastar disco.

🤖

Feito para a IA operar

Delegar o clone, a limpeza de slots ou um diagnóstico a uma IA exigia alguém no terminal respondendo prompts.MCP com o contexto das tasks (o que roda, o que já foi mesclado, o que pode ser apagado) e clone sem prompts com saída JSON. Claude Code, Codex ou Cursor criam, diagnosticam e apagam tasks sozinhos.

Recursos isolados

Um teste descontrolado numa task come toda a memória e trava a máquina inteira, com o banco de todo mundo junto.Cada task roda num slice systemd com teto de memória. Quem estoura morre sozinha; o resto segue respondendo, e o monitor diz quem foi.

📊

Monitor com ciclo de vida

Ninguém sabe o que está no ar, qual slot está livre, nem qual task já virou PR mesclado e só ocupa disco.API HTTP e MCP com o estado de cada task: PR, commits só dela, stack, CPU e memória por serviço, disco real × aparente, e um veredito: pode apagar ou não.

🧩

Agnóstico de repositório

Scripts caseiros conhecem um repositório, uma máquina e uma pessoa. Quem chega depois descobre as pegadinhas sozinho.O que muda de projeto fica em um perfil YAML, versionável; o resto o automacli descobre no compose. Serve para qualquer stack Docker.

📄

Templates a cada clone

O .env com seus segredos, o script pessoal e as instruções do agente copiados à mão em cada cópia nova.Coloque-os uma vez em ~/.config/automacli/templates/ e cada task já nasce com eles no lugar, fora do git.

O dia a dia com uma branch de cada vez ​

Um checkout só, três PRs para revisar e uma feature pela metade. Cada troca de branch custa um stash, um install e uma briga por porta. À direita, o mesmo trabalho com uma task por branch: arraste o controle e veja as portas de cada slot.

Por que não um script ou git worktree? ​

Os dois resolvem a parte do código. O que pesa numa branch com Docker é o resto: dependências instaladas, portas livres, um banco com dados, o .env e a limpeza depois. É esse resto que o automacli automatiza.

A comparação completa, com o que cada abordagem faz bem e quando o automacli não vale a pena, está em Por que o automacli?.

O repo base no centro de tudo ​

Um único clone completo, que o monitor mantém atualizado quando baseRepo.autoUpdate está ligado no perfil, serve de origem para todas as tasks. Cada task nasce dele por snapshot ou reflink em segundos, compartilhando os blocos em disco: node_modules, vendor, .venv e os caches de build existem uma vez, e os serviços com estado rodam uma vez só. Gire a cena e adicione tasks.

Seus arquivos em toda task, sem repetir ​

Tem coisa que toda task precisa e nenhum repositório versiona: o .env com os seus segredos, um script pessoal, o CLAUDE.local.md com as instruções do seu agente. Coloque-os uma vez em ~/.config/automacli/templates/<owner>-<repo>/ e cada clone já nasce com eles no lugar.

Início rápido com IA ​

Usa Claude Code, Cursor, Codex ou outro assistente? Copie o prompt abaixo e cole nele. A IA lê a documentação pelo llms-full.txt, instala o automacli, configura o token, cria o perfil do seu repositório e sobe a primeira task, pedindo confirmação antes de qualquer comando com sudo ou que altere configuração do sistema.

Abrir no Claude ↗Abrir no ChatGPT ↗
Você vai instalar e configurar o automacli nesta máquina Linux e deixar a primeira task rodando. Antes de qualquer comando, leia a documentação inteira: https://gustavo210.github.io/automacli-releases/llms-full.txt

Regras:
- Explique cada passo em uma linha antes de executar e mostre a saída relevante.
- Peça confirmação antes de qualquer comando com sudo ou que altere configuração do sistema.
- Nunca invente token, nome de repositório ou branch: pergunte quando faltar.
- Não faça commits nem altere arquivos rastreados do repositório.

Passos:
1. Requisitos: confirme git e Docker com Compose 2.24 ou superior (docker compose version). Se faltar algo, pare e diga o que instalar.
2. Instale o executável: curl -fsSL https://github.com/Gustavo210/automacli-releases/releases/latest/download/install.sh | bash. Garanta que ~/.local/bin está no PATH e confirme com automacli --version.
3. Configuração global em ~/.config/automacli/config.json: peça o token do GitHub (fine-grained, com leitura de conteúdo e de pull requests dos repositórios que vou usar) e o diretório das tasks (padrão ~/tasks). Grave githubToken e clonePath.
4. Rode automacli doctor e explique o que a máquina tem (btrfs, systemd) e o que o automacli vai usar.
5. Pergunte o caminho de um checkout do meu repositório. Nele, rode automacli init e depois automacli profile. Mostre as portas, os serviços compartilhados e os arquivos compose detectados, e ajuste o perfil comigo seguindo a página "Perfil do repositório" da documentação.
6. Pergunte a branch e o owner/repo da primeira task. Rode automacli clone <branch> -f <owner>/<repo>, entre no diretório criado e suba a stack com automacli override && docker compose up -d.
7. Ligue o MCP do automacli em você mesmo com automacli mcp setup <seu cliente> (claude-code, codex, gemini, cursor, windsurf, vscode ou claude-desktop) e me avise que, na próxima sessão, você passa a enxergar as tasks, os slots e os serviços compartilhados sozinho.
8. Termine com um resumo: o que foi instalado, onde ficou a configuração, o slot e as portas da task e as URLs para acessar os serviços.

Em 5 minutos ​

sh
# 1. Configure o token do GitHub (uma vez)
$EDITOR ~/.config/automacli/config.json      # {"githubToken": "...", "clonePath": "/home/voce/tasks"}

# 2. Crie o perfil do repositório, a partir de um checkout dele
cd ~/projetos/minha-api
automacli init

# 3. Confira o que o automacli entendeu
automacli profile

# 4. Clone uma branch como task
automacli clone minha-feature -f minha-org/minha-api

# 5. Suba a stack da task
cd ~/tasks/task-minha-feature-minha-org-minha-api
automacli override && docker compose up -d

# 6. Dê o contexto das tasks ao seu assistente de IA (Claude Code, Codex, Cursor...)
automacli mcp setup claude-code

A primeira task recebe o slot 1: um serviço que publicava a porta 3000 passa a responder em 3100; na segunda task, em 3200.
